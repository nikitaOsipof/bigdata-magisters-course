# Инженерные методы обработки и анализа больших массивов данных

Курс разработан для магистров 2-го курса. Ориентирован на изучение вычислительной оптимизации, Out-of-Core вычислений, высокопроизводительных аналитических движков, DataOps-практик и вероятностно-байесовских методов анализа данных.

Главная цель курса — сформировать готовый высокопроизводительный вычислительный каркас для вашей магистерской диссертации.

## 🚀 Быстрый старт для магистров (через инструмент `uv`)

### Шаг 1. Установите менеджер пакетов uv
Инструмент `uv` (написан на Rust) управляет окружением в 10–100 раз быстрее, чем классический pip, гарантируя нативную скорость расчетов на вашем процессоре.
* **Windows (PowerShell):** `powershell -ExecutionPolicy ByPass -c "irm https://astral.sh | iex"`
* **macOS/Linux:** `curl -LsSf https://astral.sh | sh`

### Шаг 2. Разверните окружение курса
Клонируйте вашу копию репозитория (предварительно сделав Fork). Инструмент `uv` автоматически создаст изолированное виртуальное окружение `.venv` и установит все необходимые тяжелые библиотеки:
```bash
git clone https://github.com
cd bigdata-magisters-course

# Автоматическая сборка локального окружения
uv sync
```

### Шаг 3. Запуск инфраструктуры Data Lake (MinIO S3)
Убедитесь, что на компьютере запущен Docker Desktop. Перейдите в папку инфраструктуры и поднимите локальное S3-совместимое объектное хранилище данных:
```bash
cd infrastructure
docker-compose up -d
```
*   **MinIO S3 Web Console:** [http://localhost:9001](http://localhost:9001) (Логин: `admin`, Пароль: `SuperSecretPassword123`)

### Шаг 4. Активация окружения и запуск заданий
Для запуска скриптов практик или интерактивного дашборда Streamlit используйте префикс `uv run`:
```bash
# Пример запуска практики
uv run assignments/practice_01_lazy.py

# Запуск Streamlit-интерфейса (Интерфейс откроется на http://localhost:8501)
uv run streamlit run assignments/app.py --server.port 8501
```

## 🛡️ Контроль качества кода и защита от OOM (Локальная проверка)

В рамках курса внедрены строгие стандарты промышленной DataOps-разработки. Перед каждым коммитом и отправкой Pull Request магистр **обязан** локально проверить свой код. Если проверки выдадут ошибки, автоматический робот на GitHub отклонит вашу работу на этапе CI/CD.

### 1. Проверка стиля и утечек памяти (Ruff)
Инструмент `ruff` проверяет код на наличие синтаксических ошибок, неиспользуемых переменных и опасных антипаттернов (например, накопление глобальных списков внутри вычислительных циклов, ведущее к падению системы по памяти):
```bash
uv run ruff check assignments/
```

### 2. Строгая верификация типов данных (Mypy)
Инструмент `mypy` проверяет контракты данных до запуска расчетов. Это защищает тяжелые многочасовые Big Data вычисления от падения в самый последний момент из-за случайного прилета некорректного типа данных (`None` или `str`) из грязного сырого лога:
```bash
uv run mypy assignments/
```

## 📅 Правила выполнения и Git-регламент

### 🌿 Стратегия ветвления (Git Flow)
Каждое практическое занятие выполняется в **отдельной ветке**, созданной от актуального состояния `main`.  
**Схема именования веток:** `task/practice-[номер_занятия]-[ваша_фамилия_латиницей]`  
*Пример:* `task/practice-02-ivanov`

### 💬 Стандарт оформления коммитов (Conventional Commits)
Сообщения коммитов должны быть осмысленными и оформляться по строгому формату: `<type>: <описание изменений>`.  
*   `feat` — добавлен новый функционал, решена аналитическая задача (например, реализован байесовский шаг).
*   `perf` — оптимизация производительности (перевод кода с циклов на векторизацию).
*   `fix` — исправлена ошибка в вычислительной логике или устранен Memory Leak.
*   `docs` — изменения в документации или текстовом отчете для диссертации.

*Пример:* `git commit -m "feat: реализовано инкрементальное обновление параметров Бета-распределения"`

### 🚀 Регламент сдачи работ
1. Выполните локальные проверки: `uv run ruff check assignments/` и `uv run mypy assignments/`.
2. Запушьте ветку в свой форк и создайте **Pull Request (PR)** в ветку `main` репозитория преподавателя.
3. Опишите в PR, что сделано, и приложите полученные математические оценки (например, ширину HDI-интервала или лог `EXPLAIN` из DuckDB).
4. Ожидайте прохождения автоматических тестов GitHub Actions (зеленая галочка) и последующего ручного Code Review от преподавателя.

## 🎯 Критерии оценки диссертационной части (Зачетные требования)

Итоговой аттестацией по курсу является успешная защита вычислительного Big Data каркаса вашей магистерской диссертации (мини-проекта на базе ваших исследовательских данных или предложенных междисциплинарных датасетов). 

Проект оценивается по **100-балльной системе** на основе 6 обязательных критериев:

### 1. Вычислительный Out-of-Core слой (Баллы: 20)
*   **Инженерное требование:** Полный отказ от «жадной» загрузки сырых массивов в RAM (запрещено использование `pandas.read_csv` на файлах > 1 Гб).
*   **Метод проверки:** В коде используется DuckDB или Polars Lazy API. Лог `EXPLAIN` в вашем Pull Request должен математически доказывать работу механизмов `Filter Pushdown` и `Projection Pushdown` (выборка строк и колонок «на лету» в потоке дискового ввода-вывода).

### 2. Вероятностно-байесовский или аппроксимационный слой (Баллы: 25)
*   **Научное требование:** Реализация методов снижения вычислительной сложности алгоритмов при обработке неопределенности в условиях Big Data.
*   **Метод проверки:** В проекте должен быть реализован один из изученных методов:
    *   *Вариант А (Байесовский):* Инкрементальный потоковый пересчет параметров сопряженных распределений (Beta-Binomial или Dirichlet-Multinomial) по чанкам с фиксированной памятью O(1).
    *   *Вариант Б (Аппроксимационный):* Пространственная оптимизация уникальных элементов с помощью побитового Фильтра Блума или HyperLogLog с оценкой эмпирической погрешности.

### 3. Слой промышленного качества кода (Баллы: 15)
*   **Инженерное требование:** Код должен быть застрахован от критических сбоев в процессе расчетов и оформлен по стандартам DataOps.
*   **Метод проверки:** Команда `uv run ruff check` выдает 0 ошибок (отсутствуют утечки памяти, мертвые импорты). Команда `uv run mypy` полностью верифицирует типы данных во всех ключевых функциях фильтрации, сопряжения и агрегации.

### 4. Автоматизация и DataOps-контроль (Баллы: 15)
*   **Научное требование:** Обеспечение строгой воспроизводимости научного эксперимента.
*   **Метод проверки:** Исследовательский конвейер оркеструется средой Prefect. Внедрен шаг контроля качества данных (Data Quality): при обнаружении статистического сдвига распределений признаков (Data Drift) или пропусков пайплайн автоматически блокирует расчеты, защищая итоговую статистику от искажения.

### 5. Слой интерактивной защиты гипотез (Баллы: 10)
*   **Научное требование:** Умение наглядно и интерактивно демонстрировать результаты работы диссертационному совету.
*   **Метод проверки:** Развернуто локальное веб-приложение на Streamlit. Интерфейс должен позволять пользователю менять входные параметры (например, объем выборки или априорные веса), а приложение обязано «на лету» делать быстрые точечные запросы к Parquet-файлам в MinIO S3 и перерисовывать графики плотности вероятности без перезагрузки всего массива в RAM.

### 6. Академическое оформление по ГОСТ (Баллы: 15)
*   **Научное требование:** Наличие готового текстового подраздела для вашей магистерской диссертации.
*   **Метод проверки:** К проекту прикладывается отчет (Markdown или PDF) объемом 3–5 страниц, оформленный по предоставленному ВАК-шаблону (включает схему движения данных, формулы байесовского обновления и графики сжатия неопределенности / HDI-интервалов).

### 📊 Шкала оценивания:
*   **85 – 100 баллов:** Зачет с отличием (Рекомендация Big Data компонента к публикации в научных статьях ВАК/Scopus).
*   **60 – 84 баллов:** Зачет (Инфраструктурный каркас готов к интеграции в диссертацию).
*   **менее 60 баллов:** Незачет (Код падает по памяти, содержит запрещенные циклы, либо не прошел автоматические линтеры).
